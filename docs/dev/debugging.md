# Debugging: demo data, examples, the mock model, scripted windows

Moved out of `CLAUDE.md`. Always combine a manual run with `WISP_STUDY_HOME` so the real library is not touched.

## Demo data

Demo data: `cargo run -p wisp_core --example seed -- /tmp/wisp-demo some.pdf`, then `WISP_STUDY_HOME=/tmp/wisp-demo cargo run`. The first PDF gets reading marks (a highlight with a note and a sticky note on its first page, a text box on its last), for 全库查找 to find. Further PDFs after the first become papers of the second library with their full text, which is what 写作 needs. The first paper of the second library gets a figure (a drawn western blot), three methods (one linked to that figure, one written down by hand) and two introductions, for 方法库 and 导言库 (`open:1,page:methods`). PDFs after `--supplement` are the first paper's attachments S1, S2, … (the split with a supplement beside the text: `open:0,select:0,tab:pdf,readmode,pdfbeside:1`).

## A PDF that comes out wrong

A PDF that comes out wrong: `cargo run -p wisp_core --example structure -- a.pdf [blocks|sentences|pages|outline|captions|figures|passages|apply reply.txt]` prints what the reader and the structuring make of it (its language, how many paragraphs the rules guessed and whether a model is worth asking, sentences per part; every block with its label; every sentence kept; the page text; the outline a model is asked about; the captions of figures and tables each page shows, as the figure library reads them; with `figures`, what each page draws beside text, where the file shows each figure (its caption, the piece of the page found for it, or the page it is on when that is another) and what every mention of a figure in the text leads to, as a click on a number in the reader does; the parts a model's answer gives).

A scan the system reads wrong (`ocr::SYSTEM`): `cargo run -p wisp_net --example sight -- a.pdf` prints each page's text as the system's own recognition would have it kept, and how long the file took; `--lines` prints instead the lines in the order they are read, each with the box it stands in (points from the page's top left), which shows whether the columns were told apart and where a line was cut. The first run of a newly built binary takes up to half a minute longer: macOS prepares its model for it. macOS and Windows only.

## A Word file that comes out wrong

A Word file that comes out wrong: `cargo run -p wisp_core --example docx -- a.docx [same|edit|track out.docx]` prints the paragraphs, headings and comments the reader finds; with a mode it writes the file again (unchanged; with paragraphs changed, taken out and put in and comments added; the same as tracked changes) and says whether the result reads back as what was wanted. LibreOffice is the independent check: `soffice --headless --convert-to pdf out.docx` (or `docx:"MS Word 2007 XML"`, and read that again).

## A diagram that comes out wrong

A diagram that comes out wrong: `cargo run -p wisp_core --example mermaid -- a.mmd [dark] > a.svg` writes the SVG an answer's `mermaid` block is drawn from (open it in a browser), or says why Mermaid does not read the source. In a chat with the mock model, a question containing 「试试画图」 is answered with a graph of authors, a pie and a diagram that does not parse.

## The mock model (no API key)

No API key at hand: `cargo run -p wisp_core --example mock_model -- 8787` is a fake Claude endpoint: in a chat it calls two tools and then answers (saying how many pictures it was sent, and adding a dozen paragraphs, a list and a table for a question containing 「试试长回答」; one containing 「试试卡片」 a card of 去筛选, 查找开放全文 and a reply; in the conversation that writes a manuscript, 助手写, it calls `edit_section` and puts a paragraph citing `[P1]` at the end of the section on show, or `set_outline` with three sections for a question containing 「试试大纲」, or `write_section` with one sentence for the whole of the section on show for one containing 「试试整节」: over a section with words that is the card of 助手想改动稿件, which the step `consent` / `consent:deny` answers in whichever conversation waits), asked for search queries by the guide it proposes two for PubMed, asked to screen a paper it decides by one word, asked by 写作 for search words it gives three groups, asked by the figure library about a picture it gives a legend, tags or a reading, asked by 配引用 for search words it hands each sentence back and asked which papers bear the sentences out it takes the first found for each (for a sentence containing 「试试转述」 it says that paper only restates it), asked which sentence of a paper a citation rests on (出处) it takes the first offered (none for a citing sentence containing 「试试没有」), asked to review a section of a manuscript (批注) it proposes a change to the first sentence and makes one remark on words that are not there, asked what a paper's custom fields should hold (提取) it answers each field by its kind and quotes the start of the abstract (for a paper whose text says "Few-Shot": a Select answer that is none of the options and a quotation the paper does not hold), asked to translate (with the default instructions) it hands the text back marked as translated, and asked for a picture (生图) through any of the three interfaces it draws one of the shape asked for, coloured by the description (one containing 「试试失败」 is refused), and asked the way a model that judges is asked (a System One request to `/v1/systemone`) it answers each choice with probabilities: sure of a paper that mentions Arabidopsis, torn about one that mentions a root, sure the rest are irrelevant. A second argument (`-- 8787 1500`) delays every answer by that many milliseconds, to watch a screening run; each request is printed with its model and thinking setting. Point a profile in the demo folder's `settings.json` at `http://127.0.0.1:8787` and drive the window with `WISP_STUDY_DEV=open:0,page:ask,ask:<question>`. It also answers as DeepSeek's OCR does (`POST /v1/tools/ocr`): with a provider of the `deepseek` preset pointed at it (`"baseUrl": "http://127.0.0.1:8787"`, any key), 识别页面文字 and `wisp ocr_pdf` get a page for every page the file has, written as the service writes one (Markdown headings, units as formulas, a table as HTML, a paragraph cut in two); a file whose name contains `fail` gets the failure that comes with HTTP 200. A PDF with nothing but drawings on its pages is a scan as far as the readers go.

What a service reads from its cache: `cargo run -p wisp_net --example cache_probe -- --base http://127.0.0.1:3425/v1 --model deepseek/deepseek-flash` (`--protocol openai|anthropic|responses`, where `anthropic` takes the address without `/v1`; `--tools full|reading|none|shift|drop`, `--drop <tool>`, `--pause <seconds>`, `--effort`, `--steps 4`, `--warm`, `--key`; a service on this machine needs no key). One conversation of three questions is asked of a made-up library of four papers the way the window's assistant asks, with the library's tool table, and every request's tokens are printed as the service counted them: read, read from its cache, read anew. `none` sends no tools (what the rest of a request weighs: the table is the difference), `reading` only the tools of `tools::ACROSS`, `shift` adds a tool at the end from the fourth request on and `drop` takes one out of the middle, which is what a conversation's table is kept from (`ai::Table`). Every run puts words of its own at the head of the instructions and of the first tool, so nothing an earlier run left in the cache is counted. As measured on 2026-11-26 through a local gateway: the table of 57 tools is some 16,600 tokens on DeepSeek, 14,500 on Kimi and 27,200 on Claude Opus 5.5 and Sonnet 5.5 (`compact::tokens` says 19,000); all four read 97% or more of every request after the first from the cache; a tool taken out of the middle had DeepSeek read 15,976 tokens anew and Kimi 15,367, one added at the end 1,183.

## Scripting the window: `WISP_STUDY_DEV`

Comparing how models use the tools: `cargo run -p wisp_net --example model_probe -- --base http://127.0.0.1:3425/v1 --key … --models a,b,c` (`--protocol openai|anthropic|responses`, `--runs 3`, `--cases sentence,paragraph,long,empty,rewrite,subsections`, `--steps 8`, `--effort`, `--parallel 4`, `--proxy`, `--out calls.jsonl`). Each model is asked the same things of one made-up manuscript the way 助手写 asks them: the request is `ai::chat_request` with the library's tool table and `compose::note`, its calls run through `compose::call_with` on a library in a temporary folder (no network, nothing of a real library read or sent), and it goes on until it stops calling tools. A run is judged by what became of the manuscript, not by which tool or argument the model chose: 做对, 丢了原文 (paragraphs nobody asked it to touch are gone at the end), 中途丢过 (gone after one of its calls and put back later), 被拒绝 (every writing call was refused), 没动笔; with them the writing calls that were refused, those the window would have asked about first, and the steps, seconds and tokens a run took. `--out` keeps every writing call as the model sent it, one JSON object a line, which a conversation's history does not. The cases are the `CASES` table (改一句, 重写一段, 长节里改一句 on a section of 8,000 characters, 写空的一节, 整节重写, 分成小节: the section cut into three subsections with its paragraphs in them as they were, judged by the outline and by every paragraph standing in the section or under it); a new one is an entry there with what it `Wants` of the manuscript afterwards. Because the judging does not look at the tools, the same line compares a change to a tool or to the note with what was there before: build the example in a second worktree of `main` and run both (that is how `edit_section` came to be split from `write_section`). A run costs a model some 60,000 tokens in, since the whole tool table goes with every step; a few models answering `--parallel 4` at once was fine on a local gateway.

## The release check

`WISP_STUDY_UPDATE_URL` points the release check at another address (it must answer with a redirect to this project's release page). `WISP_STUDY_UPDATE_FILES` is the folder the package and its `SHA256SUMS` are then fetched from. The whole update can be rehearsed on macOS without a release: a bundle (`X/Wisp Study.app/Contents/MacOS/wisp_study` from `target/debug`, an `Info.plist` with another `CFBundleIdentifier`, `codesign --force --sign -`), a DMG of a copy of it named `WispStudy-v99.0.0-macos-<arm64|x64>.dmg` beside its `shasum -a 256` as `SHA256SUMS`, and a local server whose `/latest` redirects to `…/releases/tag/v99.0.0`; run the bundle's binary with both variables and `WISP_STUDY_HOME`, and `40@submit` answers the question (a build run from `target/` is not a bundle and is only told of the release). The step `restore` goes back to where `session.json` says the window was, which a scripted start otherwise does not.
